## 2. 建议提交前处理

下面这些内容不影响当前数学正确性，但建议在最终提交前整理。

### 2.1 删除已经完成的 `TODO` 注释

两个函数上方仍然保留了：

```cpp
// TODO: Implement this function
```

代码已经实现，继续保留 TODO 会让阅读者误以为任务尚未完成。可以换成解释矩阵
用途或坐标约定的注释，例如：

```cpp
// Build a model matrix that rotates around the Z axis.
```

投影函数的注释更值得记录“相机看向负 Z，传入的 near/far 是正距离”，因为这比
重复说明“实现投影矩阵”更能帮助以后复习。

### 2.2 显式包含 `<cmath>`

当前代码使用了：

- `M_PI`
- `std::cosf()`
- `std::sinf()`
- `std::tanf()`
- `std::abs()`

但 `main.cpp` 没有直接包含 `<cmath>`，只是目前通过 Eigen 或 OpenCV 的间接包含
恰好可以编译。源码最好直接包含自己使用的标准库头文件：

```cpp
#include <cmath>
```

这样可以避免第三方库调整头文件后突然编译失败。

### 2.3 统一圆周率常量

文件顶部已经定义：

```cpp
constexpr double MY_PI = 3.1415926;
```

但实现中使用的是 `M_PI`，因此 `MY_PI` 目前没有用途。

`M_PI` 并不是 C++17 标准正式保证提供的常量，在当前 GCC 环境中可以使用，但换到
其他编译器时可能需要额外设置。建议二选一：

1. 使用项目已有的 `MY_PI`，并把它改成适合矩阵计算的 `constexpr float`；
2. 如果以后升级到 C++20，使用 `<numbers>` 中的标准圆周率常量。

本作业使用 C++17，因此第一种方式最简单。

### 2.4 检查 `cv::imwrite()` 的结果

当前代码忽略了 `cv::imwrite()` 返回的布尔值。当输出路径不可写、文件名没有有效
扩展名，或者图片编码失败时，程序仍可能执行 `return 0`，让调用者误以为保存成功。

建议检查返回值，并在失败时输出清楚的错误信息。还可以在写文件前检查
`filename.empty()`，空文件名时继续使用默认的 `output.png`。

## 3. 可读性改进

### 3.1 使用更准确的变量名称

`orthogonal_projection_T` 和 `orthogonal_projection_S` 实际表示的是
orthographic projection（正交投影），而不是一般意义上的 orthogonal matrix
（正交矩阵）。更清楚的名字例如：

```text
ortho_translation
ortho_scale
perspective_to_ortho
```

此外，两个函数都使用了 `angle_rad`。模型函数中它表示旋转角，投影函数中它表示
视场角，可以分别命名为：

```text
rotation_rad
fov_rad
```

这样在阅读公式时更不容易混淆。

### 3.2 使用标准三角函数重载

可以使用：

```cpp
std::cos(rotation_rad)
std::sin(rotation_rad)
std::tan(fov_rad / 2.0f)
```

`<cmath>` 会根据参数类型选择对应重载。这种写法通常比显式使用 `cosf`、`sinf`、
`tanf` 更符合现代 C++ 风格，也更方便以后调整浮点类型。

### 3.3 使用浮点字面量

为了让类型意图更清楚，可以把浮点运算中的常量写成：

```cpp
180.0f
2.0f
1.0f
```

当前代码中的整数 `180` 和 `2` 不会造成计算错误，因为参与运算的其他变量已经是
浮点数；这个建议主要是提升可读性并减少隐式类型转换。

### 3.4 用注释记录乘法顺序

这一行是投影函数中最容易再次写错的地方：

```cpp
return orthogonal_projection_S *
       orthogonal_projection_T *
       perspective_projection;
```

建议在旁边保留简短说明：代码使用列向量，所以右侧矩阵先作用，实际执行顺序是：

```text
perspective-to-orthographic → translation → scale
```

注释应解释“为什么”，而不只是重复代码做了什么。

## 4. 参数处理改进

这些不属于矩阵作业的核心评分点，但能让程序行为更可靠。

### 4.1 验证命令行参数形式

当前只要 `argc >= 3` 就会进入命令行模式，但没有检查：

- `argv[1]` 是否为 `-r`；
- 参数是否多于四个；
- `argv[2]` 是否能够转换成浮点数；
- 指定的输出文件名是否为空。

建议只接受以下三种明确形式：

```text
Rasterizer
Rasterizer -r angle
Rasterizer -r angle output.png
```

其他情况打印用法并返回非零退出码。

### 4.2 验证投影参数

作为通用函数，`get_projection_matrix()` 可以在调试构建中检查：

```text
0 < eye_fov < 180
aspect_ratio > 0
zNear > 0
zFar > zNear
```

本作业固定传入合法参数，因此不加入检查也不会影响评分。不过参数断言可以让除零、
无效视锥体等问题更早暴露。

## 5. 测试建议

不要只通过“能看到三角形”判断矩阵正确。以下测试更有针对性。

### 5.1 模型矩阵

```text
角度 0°：矩阵应为单位阵
角度 90°：(1, 0, 0) 应变为约 (0, 1, 0)
角度 -90°：(1, 0, 0) 应变为约 (0, -1, 0)
角度 360°：结果应与 0° 接近
```

浮点计算存在误差，所以比较时应使用一个很小的容差，而不是要求逐位完全相等。

### 5.2 投影矩阵

```text
视线中心的点：投影后 x、y 应保持在中心
近平面中心：NDC z 应为 1
远平面中心：NDC z 应为 -1
近平面右边界：NDC x 应为 1
近平面上边界：NDC y 应为 1
```

还可以把宽高比从 `1` 改成 `16.0f / 9.0f`，观察水平方向是否按照预期变化。

### 5.3 命令行模式

```bash
./build-ucrt/Rasterizer.exe -r 0 zero.png
./build-ucrt/Rasterizer.exe -r 20 twenty.png
./build-ucrt/Rasterizer.exe -r 90 ninety.png
./build-ucrt/Rasterizer.exe -r -20 negative-twenty.png
```

同时测试省略输出文件名时是否生成默认的 `output.png`。

## 7. 框架自身的已知现象

以下内容不属于本次两个函数的错误，不需要为了完成 Assignment 1 主动修改：

- `rasterizer.cpp` 中的深度映射使用了硬编码的 `0.1` 和 `100`，而 `main()` 给投影
  函数传入的远平面是 `50`。Assignment 1 尚未进行深度测试，因此当前画面不受影响。
- 写入临时 `Triangle` 时，同一个 `setVertex()` 调用重复了三次，结果相同，只是冗余。
- `draw_line()` 使用固定白色，所以为顶点设置的红、绿、蓝颜色不会显示在线框上。
- `set_pixel()` 的 y 轴翻转公式在 `y == 0` 时存在潜在数组边界问题；正常示例通常
  不会触发，但以后修改视口或图形位置时需要留意。

这些属于课程提供的简化框架或后续作业会扩展的部分。建议先保持作业范围明确，
不要把 Assignment 1 变成一次大规模框架重构。
